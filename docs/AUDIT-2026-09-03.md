## Critical

### C1 — The Kafka event layer does not exist yet; the README presents it as present
`contracts/proto/` contains only `auth.proto` — no event schemas, no Schema Registry. No producer or
consumer code exists in any service; auth writes outbox rows that nothing ever drains
(`OutboxEventRepository` is a bare `JpaRepository`, `grep -c kafka pom.xml` → 0). The README topic list
drifts in both directions: `user.unbanned` / `user.roles_changed` are emitted (as ad-hoc JSON maps) but
not documented; `user.created`, `message.created`, `review.created`, `report.*` are documented but exist
nowhere. **Consequence:** the GDPR `user.deleted` saga and the ban→Redis-blocklist revocation are dead
letters — other services never learn about bans or erasures. GDPR erase is currently local-only.

### C2 — `/dev` harness and seeded credentials ship in production builds
`frontend/src/app/dev/page.tsx` has no `NODE_ENV`/env gate, there is no `middleware.ts` anywhere, and
lines 14–16 hardcode `garen@demaciabook.com` / `Demacia4Ever22` as input defaults — baked into the public
JS bundle of any prod build. That's a known-password account plus an anonymous gateway introspection page.

### C3 — The admin service cannot start as configured
`services/admin/src/main/resources/` contains only `application.yml`, but Flyway points at
`classpath:db/migration` (application.yml:15) — with Boot's default location check the app fails at
startup. Independently, the compose healthcheck probes `/health/ready` (docker-compose.yml:237) and no
controller serves it, so the container could never be reported healthy anyway. The README's
"`/health/live` + `/health/ready`" claim for admin is false.

### C4 — No Docker image is ever built in CI
CI has no docker job, so the first build of every image happens at deploy time — the
`additional_contexts: contracts` COPY, the Python final stages, and messaging's dep-copy are all
untested failure modes. Compounding: 4 of 7 Dockerfiles (messaging, presence, assets, admin) run as
root, and there is no `.dockerignore` anywhere — Python images bake in the local `.venv`.

## Claims vs reality

The auth service's "fully OWASP-audited, all findings remediated" claim is **mostly but not fully
true** post-migration. Verified solid: refresh rotation (SHA-256-hashed, atomic consume, theft detection
in `REQUIRES_NEW`), anti-enumeration dummy-hash + identical envelopes, bcrypt cost 12 with a 72-byte
input cap, HMAC OAuth state with constant-time compares, rank guards, constant-time gRPC secret check,
and a clean Boot 4.1.1 migration (208/208 green; main-code diff was Jackson-namespace swaps).
Outstanding remediation gaps:

1. **PII survives "erase"** — `ip_address`/`user_agent` persist in refresh tokens for 30 days, the
   verification-token identifier keeps the email, ban/warning reasons and audit_log rows persist
   indefinitely (`AdminService.erase`, `RefreshTokenCleanupJob`).
2. **Password spraying is unthrottled** — login limits are per-email only; the README credits the
   gateway with rate limiting and a Redis blocklist, and neither exists (the gateway's own docs admit it).
3. **Dev gRPC secret fail-fast fires only under `SPRING_PROFILES_ACTIVE=prod`**, while compose defaults
   `GRPC_INTERNAL_SECRET:-dev-internal-secret`.

Also drifting from reality: presence and assets `/health/ready` return 200 unconditionally without
touching their dependencies (compose health gates are decorative for both); `deploy/k8s/` is empty, not
"stubs"; the database-per-service claim is nominal at the DB layer — every service shares the `om`
superuser role across all 6 databases.

## Important (should fix)

- **Catalogue:** JWKS refresh holds a lock across a blocking 10s HTTP fetch with no negative caching —
  an auth outage serializes every request into a self-DoS (Program.cs:172–202). PATCH-vs-accept snapshot
  race (documented, cheap to close). Plaintext internal hops with no Production transport guard.
- **Auth:** ban-then-refresh returns `401 refresh_token_reused` instead of the documented
  `403 account_banned`; `/health/ready` leaks raw DB exception text; admin search doesn't escape LIKE
  wildcards; `setRoles` allows equal-rank changes (unlike ban/warn).
- **CI:** the only dependency scan is advisory (`continue-on-error`) and Java-only — no govulncheck,
  pip-audit, or npm-audit; no SBOM; `go-version: stable` unpinned; gateway on go 1.25 vs messaging 1.23.
- **Compose:** jaeger/mailpit on `:latest` with ports on 0.0.0.0 (tracing UI + open SMTP on the LAN) vs
  postgres's disciplined 127.0.0.1; no resource limits or restart policies.
- **Messaging:** `healthReady` opens a fresh DB pool per probe with no `connect_timeout`; no http.Server
  timeouts at all.
- **Frontend:** zero security headers (no CSP/HSTS/X-Frame-Options; `X-Powered-By` leaks); rewrite
  destination hardcoded to `localhost:3000` with no env override; no CSRF story beyond SameSite+JSON —
  acceptable now, must become deliberate before chat/listings ship.
- **Admin:** no spring-boot-starter-security groundwork; `show-details: always`.

## Minor (selected)

Messaging `/` is a catch-all returning 200 for unknown paths; EXPOSE mismatches (messaging 8080 vs 8082,
admin 8080 vs 8085); `generate.sh` hardcodes a macosx_x64 plugin path; catalogue duplicate-create with a
replayed idempotency key surfaces as 500 not replay; app-clock vs DB-clock in the expiry predicate;
unbounded reads on `/me` endpoints; dev-api spread-then-overwrite drops future custom headers; stale
"no JwtAudienceValidator in this Spring Security version" comment; `SecurityMatchersContractTest` still
says "Boot 3.3.x"; `shadcn` CLI listed as a runtime dependency.

## What is genuinely strong (verified, not trusted)

- **Gateway edge:** client XFF is overwritten, never appended; identity/forwarding headers stripped and
  regression-tested; introspection fails closed with a 1s deadline and bounded upstream waits; public
  routes are exact-match on mux-normalized paths (no bypass via `//`, `%2e`, trailing slashes); an honest
  `/health/system` probes every upstream with URL redaction.
- **Catalogue:** deny-by-default fallback policy; ownership enforced inside the query predicate on every
  mutation; FCFS accept is genuinely atomic (conditional `ExecuteUpdate` decides the winner by rowcount,
  unique index backstop, outbox in the same transaction, xmin concurrency → 409); tests run against real
  Postgres via Testcontainers with real RSA-signed tokens; Production fail-fast for dev-default secrets.
- **Auth:** the deep flows (rotation, theft detection, enumeration controls, OAuth state, rank guards)
  match the security docs, and the Boot 4 migration is clean.
- **Frontend:** httpOnly-cookie model with zero token juggling in JS, same-origin rewrites, no XSS sinks,
  and a real CI test gate.
- **Compose where it matters:** postgres loopback-only, gateway as the single published port, pinned
  subnet so exactly one container is a trusted XFF proxy, JWT signing key on a persistent volume.

## Recommended fix order

1. **Frontend (minutes):** gate `/dev` out of prod builds; drop the seeded credentials.
2. **Admin (small):** add `db/migration` + `/health/live`|`/health/ready` (or point compose at actuator) —
   currently the stack can never be fully healthy.
3. **Auth:** outbox relay (a scheduled poller suffices to start) or soften the saga claims until it
   exists; scrub PII at erase time; make the dev-secret fail-fast unconditional off localhost.
4. **CI:** docker build gate for all 7 images; add pip-audit/npm-audit/govulncheck to the advisory lane.
5. **README truth-pass:** rate limiting, blocklist, event topics, k8s status, test counts, readiness honesty.
6. **Containers:** non-root + `.dockerignore` for the 4 root images; per-service DB roles; bind
   jaeger/mailpit to 127.0.0.1.
7. **Catalogue:** fetch JWKS outside the lock with a short negative cache.

# Addendum: Test-Quality & Gaming Audit (same day)

Question: are the tests a real spec, or were they edited to pass? Method: (1) forensics over
every commit that touched both test and production code, (2) per-suite quality review by
independent auditors, (3) fault injection — deliberately breaking load-bearing code to prove
suites go red.

## Verdict: no gaming found

- **History:** ~40 commits touch tests+code together; every one is a deliberate `fix:`/`feat:`
  whose tests were updated to pin the *new* behavior, and diff review shows assertions only
  strengthened over time (e.g. `d0c8055` replaced check-then-act asserts with atomic-UPDATE
  verifies; `eed094f` added the positive non-throttled case). The Boot-4 migration commit
  (`7db8125`) changed test imports mechanically — zero assertion changes. No deleted or
  de-skipped tests.
- **Current suites:** no tautologies, no mock-echo assertions, no expected-values computed from
  the code under test, no catch-and-pass. Catalogue's race test is real (fires both accepts
  concurrently, asserts DB count == 1).
- **Fault injection (red-team):**
  | Injected fault | Result |
  |---|---|
  | gateway: disable identity-header stripping | **RED** — `planted identity header must be stripped, got "victim"` |
  | frontend: drop forced JSON content-type | **RED** — `forces the JSON content-type header` fails |
  | auth: disable rate-limit check | **RED** — 2 rate-limiter tests fail |
  | catalogue: delete in-transaction expiry predicate from FCFS accept | **PASSES — real blind spot** |
  | gateway: convert XFF overwrite→append | property still holds: Go's `Rewrite` mode strips XFF before the callback, so the stdlib already enforces it; the service's `Del` is redundant defense-in-depth |

## Real finding: one unguarded guard

`accept_lapsed_listing_is_410_even_before_sweep` (SecurityAndFlowTests.cs) pins the **pre-check**
path, but the in-transaction expiry predicate (`ListingEndpoints.cs:317`) — the closure for the
check-vs-update lapse race — can be deleted with zero test failures (verified by injection with a
clean rebuild). This is the same structural blind spot the team already fixed for xmin in
`3d59490` (moved to persistence level). Fix: give the accept path an injectable clock and pin the
predicate at persistence level, like the xmin pin.

## UNGUARDED registry (behavior claimed, no test would fail if it regressed)

- **auth:** cookie `Secure`/`SameSite` flags (only httpOnly/maxAge/path are pinned); rollback
  survival of refresh-family revocation (deferred to Testcontainers per class javadoc); limiter
  wiring on controllers (services mocked in contract tests).
- **catalogue:** the in-tx expiry predicate (above); HTTP-level 409 mapping of the xmin
  concurrency exception; ILIKE search escaping (`%`/`_`/`\`); cross-user scoping of PATCH,
  watchlist and trades endpoints.
- **gateway:** percent-encoding/trailing-slash normalization; `internal/authclient` and
  `internal/httpx` packages have zero tests; the deployed route set in `main()` (tests inject
  their own maps).
- **frontend:** newest-first ordering with 2+ calls (test clicks only one button).
- **presence/assets:** smoke-only (status codes, not bodies; readiness currently can't fail).

## Documentation state

- `services/auth/docs/testing.md` — spec-grade (three-layer model, per-file "what it pins"
  tables, an explicit "deliberately NOT tested" section). **Stale:** says ≈140 tests, actual 208.
- `services/gateway/docs/testing.md` — exemplary, includes a mutation gauntlet. **Stale:** says
  17 tests, actual 26; hung-upstream and catalogue-mount tests unlisted.
- **catalogue:** no testing doc; README says 30 tests, actual 31.
- **frontend:** no test doc (names are good, 10 tests). **presence/assets:** one docstring each.

## Recommendations

1. Fix the catalogue expiry-predicate blind spot (injectable clock + persistence-level pin).
2. Refresh both stale `docs/testing.md` files; add a short one for catalogue and frontend.
3. Adopt the rule the history already follows, written down: behavior changes may update tests,
   only with the reason in the commit message; assertions never get weaker silently.
4. Add the cheap missing pins from the UNGUARDED registry (cookie flags and search escaping are
   one-liners; the rest are small).
